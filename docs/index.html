Living PRD (Product Requirements Document)

Updated every week as we test with real users and learn what works.

1. Target User & The Job to Be Done

Who is this for? Comms firms that do news roundups for clients across multiple domains. E.g., when I worked at a PR agency, we would do a weekly newsletter for a B2B payments company, focused on news across FX, macroeconomics, fraud, etc..

The painful "Before" workflow: We manually search the web for the most relevant news in those categories from that week. We have access to subscriptions, but the company does not so if there's a paywall, they won't be able to read it.

The "After" workflow with this product: The tool scours the web for the relevant articles that week per category. It hyperlinks the direct link to the site and gives a 3 sentence summary of the article. For articles that require a subscription, users can upload a PDF of the article and the tool will include it in the newsletter and summarize it for them. The tool summarizes and links them without having to store login credentials.

2. Scope & Explicit Non-Goals

  • In Scope (Core Workflow): Automates newsletter creation based on industry categories and solves the paywall issue. It finds candidate articles per category from news feeds and search, then ranks them by relevance. It drafts a 3-sentence summary of each article. User reviews and edits the picks then is able to email the newsletter directly to client.
  • Out of Scope #1: Sending newsletters to clients automatically. The tool only produces a draft newsletter that a human approves and sends through the agency's email.
  • Out of Scope #2: Storing and using an agency's paid subscription credentials. The tool will use RSS feeds, news search APIs, and publicly available sites first.
  • Out of Scope #3: Storing or redistributing full paywalled articles; PDFs are used only to write the summary.

3. How It Works Under the Hood & Riskiest Assumption (PRD v2 · Build 2)

Riskiest Assumption: AI can pick the same articles a PR professional would pick for a client's category, and can summarize them accurately from only the headline and a short description, without reading paywalled full text. If either part fails, the user has to redo the search and rewrite every summary manually.

How Build 2 tests it: One full user action now runs on data with an AI call. For each category, Claude (Haiku 5.5) scores 20 candidate articles from 0 to 10 and summarizes the top 5.

  • Picking: Before AI scoring, ranking was "priority source first, then newest." With Claude scoring, the same search returned fake-bank-account scams, card fraud results and a central bank fraud-reporting rule. Scoring is based on criteria including topic fit, client impact, newsworthiness, and source & format.
  • Summarizing: The first summaries were filler ("It is a daily currency market update"). I tightened the instructions, although the summaries are still pretty thin because it only has access to the headline and subheadline. Need to figure out a way to get more of the article body.
  • Freshness: Google News occasionally returned old stories (one from 2015), so every source now has a hard 7-day cutoff.
  • Still unproven: whether a PR professional agrees with Claude's picks. Every removal is saved with Claude's score, which sets up the Build 4 evaluation.

How the app works:

  1. The user enters the client, priority sources and categories (with optional search terms and excluded words).
  2. For each category, the local Python server searches four sources at once: Google News for the priority sources, Google News across all outlets, 10 publisher RSS feeds (Bloomberg, NYT, FT, WSJ, TIME), and the GNews API. Reuters and Barron's have no public feeds, so they are searched through Google News.
  3. Articles older than 7 days or without a date are dropped, and the same story from two sources is merged.
  4. The best 20 candidates go to Claude in one request. It returns a relevance score and a summary for each as structured JSON. The top 5 are shown; anything under 5/10 goes to a "filtered" pile that the user can still open.
  5. The user reorders or removes articles (with a reason) and adds paywalled ones by uploading a PDF of the article: Claude reads it and fills in the headline, source and a summary for the user to check (about $0.0004 per article; the PDF is not saved). Then the user copies an email-ready draft.
  6. If Claude is unavailable, the app falls back to ranking by source and date, so the workflow never breaks.

Simple Architecture: Client categories, keywords, priority sources → server pulls this week's articles from Google News, publisher RSS feeds and GNews → 7-day cutoff and de-duplication → Claude Haiku 5.5 scores relevance and writes summaries → user reviews and edits → user copies the newsletter draft and sends it to the client. Build 3 · Build.exe: The Core Workflow (Due Nov 23)

  • What shipped: Press Pass is live at ss11807-battlecardbuilder.onrender.com (Beginner lane: Ship it). People sign in with email and password (Supabase Auth), and each account keeps its own saved client setups, past newsletters and article-removal feedback, with Row Level Security on every table. Search moved to Exa (news from the last 7 days, with article highlights) plus the NYT Article Search API, and each category has a new "What it means for this client" field to keep results on topic. The paid routes need a sign-in and have per-user hourly limits. Full audit in SECURITY.md.
  • What broke / changed in PRD: My first real test run failed: I removed 13 of the 15 articles that made the cut. "Hardware Security" pulled in BitLocker and Nvidia stories instead of crypto hardware wallets, the same Coinbase story appeared twice, summaries just repeated the headline (Google News only provides headlines), and every card said 9/10 with no reason. Switching to Exa and NYT and adding category descriptions is the first fix; duplicate detection, explained scores with a stricter cutoff, and real summaries come next. The first Render deploy failed because the service was connected to an old copy of the class template instead of this repo. The live security check found that the server's own code was downloadable (no secrets in it), so the site now serves only its three public files. Email confirmation is off because Supabase's free email can't reach outside addresses.
  • Things learned with AI: How Row Level Security keeps each user's rows private, why a publishable key can sit in the browser but a secret key can't, what changes when an app leaves localhost (PORT, environment variables, files that vanish on restart), rate limits as a spending guard, and pinning a CDN library with an integrity hash.
  • Security test: Signed in as a second account on the live site: it sees "No newsletters yet" and none of the first account's data. A scripted check on the live site passed 39/39 (no reading, changing, deleting or planting another account's rows), and the paid routes refused requests without a sign-in.
  • Cost & time this week: $0.09 ($0.04 Claude API + $0.05 Exa search; NYT, Render and Supabase are free) · 5 hours
